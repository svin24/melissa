# Melissa — project plan

Status: draft v0. Agents may expand any section; keep decisions and open questions up to date.

## 1. Vision

Melissa is an open source, clustered, agent-run, immutable self-hosting OS. A user installs it on one or more
machines, and an AI agent runs the infrastructure: installing apps from a fixed catalog, updating, backing up,
and healing.

Naming:
- **Bee** — a node running Melissa. Each bee can run its own local agents.
- **Hive** — the cluster of bees.
- **Queen bee** — the master agent that coordinates the hive (scheduling, upgrades, policy). Bees stay useful without it.

Agent backends are pluggable. A bee may be a "dumb box" with no LLM at all, or use external LLM subscriptions
(Grok, Claude, OpenCode with models such as Gemma). Local models are optional.

A VPS can join as a bee for: offsite backups (restic or Kopia), public ingress (important behind CGNAT such as
Starlink), VPN exit, seedbox. The VPS is **kept out of the control plane**: it is a worker/edge, never holds
cluster-admin credentials or the queen bee.

Goals: boring and reliable, immutable and atomically updatable, works on a LAN without internet for the UI,
easy for others to fork and build on.
Non-goals (for now): a general-purpose desktop distro, a custom UI generated by AI, supporting every hardware type.

## 2. Base OS and image pipeline

- **Now:** Fedora Kinoite, dogfooded on the developer laptop. Develop the custom image there.
- **Custom image:** a bootc image built from a `Containerfile` (starting `FROM` the Kinoite bootc base, later a
  Melissa-branded base). Move an installed system onto it with `bootc switch <image>`; roll back with `bootc rollback`.
- **Headless variant (later):** `quay.io/fedora/fedora-bootc` based image for servers and VPS-like bees.
- **Testing:** VMs (libvirt/QEMU) for multi-node hive tests; disposable bees from the same image.
- **Update distribution:** images are published first to `ghcr.io`. Later a Cloudflare-fronted or custom registry
  domain; clients migrate through `registries.conf` mirrors (no reinstall needed). Sign images (cosign) before any public release.
- **BuildStream:** a cleaner reproducible build is "later later". Not before the product works.

## 3. Cluster layer

- **Orchestrator:** k3s (single binary, fits small boxes). Node labels describe roles (`melissa.io/role=storage|gpu|edge|gaming`, final label domain TBD).
- **Ingress:** wildcard `*.<domain>` (e.g. `nextcloud.<domain>`, `immich.<domain>`) via the k3s ingress controller, with automatic TLS (internal CA on LAN, ACME for public).
- **HA virtual IP:** kube-vip or keepalived for the control-plane/ingress address.
- **Storage:** Longhorn first (simple), Ceph (Rook) for larger hives. Local-path for single-node M2.
- **Apps:** app manifests (see Web UI) render to Helm charts/kustomize. Initial catalog: Nextcloud, Immich.
- **Gaming node (later):** KubeVirt with GPU passthrough (VFIO) running SteamOS/Windows VMs, streamed through Sunshine/Moonlight.

## 4. Networking and access

- **Mesh:** Tailscale with pre-auth keys by default; Headscale (self-hosted control server) or NetBird as alternatives. Abstract it behind a small Go interface so the mesh is swappable.
- **Two access modes for remote use:**
  1. *Hosted relay with login* — user signs in to a hosted service that relays to their hive (like T3 Connect with an auth provider such as Clerk). Easiest for non-technical users.
  2. *Bring your own Tailscale* — the user joins their own tailnet; no Melissa-run service involved.
- Public exposure goes through an edge bee (VPS) over the mesh, not by opening home router ports.
- The LAN UI must keep working with no internet.

## 5. Agent layer

- Multi-backend agent abstraction in Go: Claude (Opus 5.5), Grok, OpenCode (Gemma, etc.), later others. One interface for sessions, tool calls, streaming and cancellation.
- Agents act through a **narrow tool API** (install app, scale, back up, restore, update, inspect health), not raw root shells. Every mutating action is logged and, per policy, requires confirmation.
- Queen bee coordinates; each bee may run local agents scoped to that bee.
- **Reference:** T3 Code (github.com/pingdotgg/t3code) is a useful reference for multi-agent, many-backend UX. It is currently published under the MIT license — re-verify the license and notice requirements before reusing any code; otherwise treat it as inspiration only.

## 6. Web UI

- Headless OS, so the UI is a web app served by the bee. Stack: **Go `html/template` + htmx**, assets embedded with `go:embed` (no CDN, works offline). Optional Alpine.js for tiny client state, Pico.css for styling. Pin and vendor all assets.
- Rationale: light, stable, little churn, nothing that needs constant updating; easy for contributors to extend.
- **Fixed component library + app manifests.** The UI is built only from a reviewed set of components (cards, tables, forms, logs, status badges, confirm dialogs). Apps declare their needs in manifests (name, icon, ports, storage, config fields, health checks). **AI agents must NEVER generate custom UI elements.** They only select components and fill manifests. New components are human-reviewed code.
- Auth: local accounts + passkeys later; sessions with CSRF protection from day one.

## 7. Language and code layout

Go for everything (daemon, CLI, agent layer, UI server). Suggested layout:

```
cmd/melissad      # per-bee daemon
cmd/melissa       # CLI
internal/agent    # backend abstraction (claude, grok, opencode)
internal/hive     # cluster state, bee discovery
internal/web      # handlers, templates, components (go:embed)
internal/mesh     # tailscale/headscale/netbird adapters
manifests/        # app manifests (nextcloud, immich)
image/            # Containerfile(s), bootc config
docs/
```

## 8. Licensing and legal

- Open source so others can build on it. Candidate: **AGPL-3.0 plus a commercial license/EULA (dual license)** for those who cannot use AGPL. Alternatives (Apache-2.0/MPL) if community growth matters more than protecting the commercial path.
- Dual licensing requires owning the copyright: either a **CLA** (e.g. CLA Assistant) for outside contributors, or keep development internal-only until the license is settled. Decide before accepting external PRs.
- **Name risk:** Melissa Data holds MELISSA trademarks in classes 9 and 42 (US/UK/EU). Get a legal/trademark check before any commercial launch; have a fallback name ready (the owner decides any rename; agents must not rename the project).
- Candidate identifiers (appeared unregistered on 2026-11-17, not reserved): domain `getmelissa.dev`, GitHub org `getmelissa`. Re-check availability before relying on them.
- Keep the project separate from any employer: no outside code or assets.

## 9. Milestones

**Demo (target: end of the current week):** multi-agent demo on the laptop showing Claude, Grok and OpenCode (Gemma) as backends behind the same agent interface, coordinated by a minimal queen bee, with a minimal web UI that lists agents and lets one install/inspect something. Scripted and repeatable.

Roadmap (rough, phases may overlap):
- **M0 — Repo + image:** repo scaffolding, local builds, a bootc image of Kinoite running on the laptop via `bootc switch`, rollback verified.
- **M1 — Queen bee + UI skeleton:** agent abstraction with three backends, narrow tool API, Go + htmx web UI with the base component library, audit log.
- **M2 — Single-node k3s + apps:** k3s on one bee, wildcard ingress, manifest format, Nextcloud and Immich installable from the UI.
- **M3 — Multi-bee:** hive of VMs, mesh via Tailscale, bee join flow, node labels, queen bee failover design, shared storage (Longhorn).
- **M4 — VPS bee + backups:** edge/ingress bee, offsite backups with restic or Kopia, restore drills, VPN exit, seedbox as optional apps.
- **M5 — Headless image:** fedora-bootc based image, installer/first-boot flow, image signing and update channel on ghcr.io.
- **Later:** gaming node (KubeVirt + GPU + Sunshine/Moonlight), Cloudflare/custom registry mirror, BuildStream, hosted relay access mode, Ceph.

## 10. Open questions

1. Final license (AGPL + commercial vs. alternatives) and CLA vs. internal-only development.
2. Trademark clearance for "Melissa" and the fallback name; confirm domain/org choices.
3. Hosted relay mode: build our own or integrate an existing service? Who runs it and what does it store?
4. Mesh default: Tailscale (easy, third-party control plane) vs. Headscale/NetBird (self-hosted). What is the default for new users?
5. Longhorn vs. Ceph thresholds; minimum hardware for a bee.
6. Queen bee placement and failover: pinned to one bee, or elected? What happens with no LLM backend available?
7. Agent permission model: which actions are autonomous vs. need confirmation? Audit log format.
8. Can T3 Code code be reused (license is MIT today)? Or only used as a design reference?
9. App manifest schema: own format vs. Helm/Compose-based? How are app updates and data migrations handled?
10. Secrets management for apps and backends inside the cluster (e.g. sealed secrets / external vault).
11. Update safety: how do bees stage, verify and roll back bootc updates across the hive?
12. Image base: stay on Kinoite (KDE) for desktop bees, or headless-only for all bees except the dev laptop?
