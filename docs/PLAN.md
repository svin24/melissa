# Melissa — project plan

Status: draft v0. Agents may expand any section; keep decisions and open questions up to date.

## 1. Vision

Melissa is an open source, clustered, agent-run, immutable self-hosting OS. A user installs it on one or more
machines, and an AI agent runs the infrastructure: installing apps from a fixed catalog, updating, backing up,
and healing.

Naming:
- **Bee** — a node running Melissa. Each bee can run its own local agents.
- **Hive** — the cluster of bees.
- **Queen bee** — the master agent that coordinates the hive (scheduling, upgrades, policy). Bees stay useful without it.

Agent backends are pluggable. A bee may be a "dumb box" with no LLM at all, or use external LLM subscriptions
(Grok, Claude, OpenCode with models such as Gemma). Local models are optional.

A VPS can join as a bee for: offsite backups (restic or Kopia), public ingress (important behind CGNAT such as
Starlink), VPN exit, seedbox. The VPS is **kept out of the control plane**: it is a worker/edge, never holds
cluster-admin credentials or the queen bee.

Goals: boring and reliable, immutable and atomically updatable, works on a LAN without internet for the UI,
easy for others to fork and build on.
Non-goals (for now): a general-purpose desktop distro, a custom UI generated by AI, supporting every hardware type.

## 1b. Hive model

Binding spec: [HIVE-MODEL.md](HIVE-MODEL.md) (owner, 2026-11-18), diagram `hive-model.svg`. Apiary > Hive > Comb
(device, one Queen each; the main comb's Queen has the final say) > Bees (worker agents) > Cells (one bee's area of
responsibility) > Services (workloads). Terms are internal roles; display names are chosen by the user or by a Queen.
**Status (2026-11-18):** the code follows the model on one comb: `crates/comb`, comb/bee ids, persistent named
bees with their own resumable sessions, cells owned by bees (namespace labels + admission), reassign only by the
Queen with the user's yes or by the user, user chat with any bee, bee-to-bee only via the Queen. Mapping table in
HIVE-MODEL.md; details in `docs/agent-skills/cells-and-ownership.md` and `queen-loop.md`. Multi-comb is M3.

## 2. Base OS and image pipeline

- **Two image variants from day one**, built from one `image/Containerfile` (`VARIANT=desktop|headless`) that
  shares a Rust build stage and the Melissa layer (binaries, units, Tailscale, config under `/usr/lib`):
  - **desktop**: `FROM quay.io/fedora-ostree-desktops/kinoite:45` (KDE). For the dev laptop and desktop bees.
    Ships the transient-root `prepare-root.conf` (needed for Nix) and Tailscale, which the laptop currently has as
    host-side rpm-ostree changes. Runs the full server like headless (system queen as `melissa`, k3s, web UI on
    127.0.0.1:8080 at boot, whoever is logged in); no first-boot account prompt (KDE has its own setup).
  - **headless**: `FROM quay.io/fedora/fedora-bootc:45`. For servers, mini PCs and VPS bees. The queen runs as a
    system service as the fixed system user `melissa` (config in `/etc/melissa`, state in `/var/lib/melissa`, agent CLIs
    and their logins in `/var/lib/melissa/home`, set up with `sudo melissa-setup agent <name>`; DynamicUser until 2026-11-18).
  - Both bases carry `containers.bootc=1` (verified with skopeo, 2026-11-18).
- **Dev laptop:** currently stock Kinoite 45 from the ostree remote. **Switch deferred (owner, 2026-11-18):** develop on
  the headless image in a QEMU VM until there's much more to it; the desktop image is built and VM-tested meanwhile. It moves onto the desktop image with
  `bootc switch` only after the image passed VM tests, and only with the owner's explicit yes; roll back with `bootc rollback`.
- **Packages:** extra packages go into the image (owner's preference, for ease of use), listed in
  `image/packages-{common,desktop,headless}.txt`. No host-side layering.
- **Testing:** QEMU VMs (KVM, UEFI) from disks built with bootc-image-builder (`just vm-disk`, `just vm-run`);
  later multi-node hive tests with disposable bees from the same images.
- **Update distribution:** images are published first to `ghcr.io`. Later a Cloudflare-fronted or custom registry
  domain; clients migrate through `registries.conf` mirrors (no reinstall needed). Sign images (cosign) before any public release.
- **BuildStream:** a cleaner reproducible build is "later later". Not before the product works.

## 3. Cluster layer

- **Status (2026-11-18):** k3s v1.37.2 ships in both images (enabled on headless), pinned by sha256 in
  `image/k3s.lock`, airgap images in `/usr`, k3s-selinux 1.6 with SELinux enforcing, Traefik telemetry off. Smoke test
  passes in the headless VM (node Ready, no AVC denials, ingress reachable). See docs/agent-skills/k3s-on-bootc.md.
- **Queen ↔ k3s (2026-11-18):** the queen talks to the API as ServiceAccount `melissa/melissa-queen` with read-only
  RBAC (get/list/watch on nodes, namespaces, pods; no Secrets, no writes). A root oneshot
  (`melissa-kubeconfig.service`) writes its kubeconfig to `/run/melissa-kube` (root:`melissa-kube` 0640); the
  queen service has that group, does not wait for k3s at boot and re-reads the file on each cluster call.
  Client: kube-rs over rustls in `crates/hive`.
- **App installs (2026-11-18, M2 core):** catalog of reviewed TOML manifests (`manifests/`, shipped in
  `/usr/share/melissa/catalog/`; `crates/catalog`), rendered to Namespace `app-<name>` + RoleBinding +
  Secret + PVC + Deployment + Service + Traefik Ingress (`<app>.melissa.home.arpa` by default,
  `[apps] domain`) and server-side applied by a second identity, `melissa/melissa-apps`, whose writes
  admission policies pin to `app-*` namespaces with Pod Security baseline (no Secret reads anywhere).
  Tools: `list_catalog`, `list_apps`, `install_app`, `app_status`, `app_logs`, `stop_app`, `start_app`,
  `uninstall_app` (stop/start since 2026-11-19: stop keeps everything, always asks, never "destructive"). First app: Nextcloud
  34.0.6 (official Apache image by digest, SQLite). Verified in the headless VM: install with
  confirmation, ready, `status.php` from the host, owner login, logs cap, keep-data uninstall +
  reinstall, delete-data uninstall, RBAC denials, smoke test, no AVC denials. Details:
  `docs/agent-skills/app-catalog.md`.
- **Orchestrator:** k3s (single binary, fits small boxes). Node labels describe roles (`melissa.io/role=storage|gpu|edge|gaming`, final label domain TBD).
- **App links (2026-11-19):** by default `http://<device address>:<port>`: each app gets its own NodePort from
  30000-30079 (`<app>-port` Service, recorded in `melissa.io/port`), reachable on the LAN and over Tailscale with no
  DNS; the web UI builds links from the address the visitor used. See DECISIONS.md.
- **Ingress:** wildcard `*.<domain>` (e.g. `nextcloud.<domain>`, `immich.<domain>`) via the k3s ingress controller, with automatic TLS (internal CA on LAN, ACME for public). Today an extra option for people with their own DNS (`dns_url`).
- **HA virtual IP:** kube-vip or keepalived for the control-plane/ingress address.
- **Storage:** Longhorn first (simple), Ceph (Rook) for larger hives. Local-path for single-node M2.
- **Apps:** Melissa's own app manifests (TOML, see above and DECISIONS.md) render to plain objects;
  no Helm/kustomize. Initial catalog: Nextcloud (done, SQLite; Postgres later), Immich next.
- **Gaming node (later):** KubeVirt with GPU passthrough (VFIO) running SteamOS/Windows VMs, streamed through Sunshine/Moonlight.

## 4. Networking and access

- **Mesh:** Tailscale with pre-auth keys by default; Headscale (self-hosted control server) or NetBird as alternatives. Abstract it behind a small Rust trait so the mesh is swappable.
- **Two access modes for remote use:**
  1. *Hosted relay with login* — user signs in to a hosted service that relays to their hive (like T3 Connect with an auth provider such as Clerk). Easiest for non-technical users.
  2. *Bring your own Tailscale* — the user joins their own tailnet; no Melissa-run service involved.
- Public exposure goes through an edge bee (VPS) over the mesh, not by opening home router ports.
- The LAN UI must keep working with no internet.

## 5. Agent layer

- Multi-backend agent abstraction in Rust (a trait per backend, async streams): Claude (Opus 5.5), Grok, OpenCode (Gemma, etc.), later others. One interface for sessions, tool calls, streaming and cancellation.
- Agents act through a **narrow tool API** (install app, scale, back up, restore, update, inspect health), not raw root shells. Every mutating action is logged and, per policy, requires confirmation.
- Queen bee coordinates; each bee may run local agents scoped to that bee.
- **Status (2026-11-18):** `crates/agent` has the `Backend` trait, a built-in `echo` backend (no LLM), a CLI
  backend that drives `claude -p`, `grok -p` and `opencode run` (all verified working), a task board with
  cancel/timeout/output cap, and a JSONL audit log.
- **Tools (2026-11-18):** narrow tool API with label-based policy, confirmation store and audited calls
  (`crates/agent/src/tools`), served to agent CLIs over MCP (`crates/agent/src/mcp.rs`, `POST /mcp/<token>`).
  Claude runs with no built-in tools and only Melissa's (verified). First tool: `comb_info`. The confirmation
  inbox needs UI (waiting for the owner's UI ideas); Grok and OpenCode get tools via ACP, Claude sessions via
  stream-json (below).
- **Sandbox (2026-11-18):** every agent CLI runs under bubblewrap by default (`crates/agent/src/sandbox.rs`):
  read-only `/usr` and `/etc`, private `/tmp`, empty read-only home with only the CLI's credential file(s), the
  task workdir as the only writable host path, own PID/user/IPC/UTS namespaces, no capabilities, dies with the
  queen's task. Verified with claude (incl. MCP tool calls), grok and opencode. Next: seccomp, Melissa-owned
  CLI logins.
- **Egress (2026-11-18):** deny-by-default network for every sandboxed agent (`crates/agent/src/egress`): own
  network namespace with loopback only and no resolver; `melissa-netbridge` inside forwards to per-sandbox Unix
  sockets served by the queen: an HTTPS `CONNECT` proxy with a per-backend host allowlist (DNS by the queen,
  non-public addresses refused, limits, every decision audited as `egress.allow|deny|error`) and an MCP-only
  endpoint (the rest of the queen's API is unreachable from agents). `network = "proxy"` (default) | `"learn"` |
  `"none"` | `"host"`, `allow = [...]` per backend; built-in allowlists found with learn mode. Verified live on
  the laptop: claude + comb_info, grok-acp + comb_info, opencode, and the Queen with a worker, all under
  `proxy`, with telemetry (Datadog, Mixpanel, grok.com) denied; `curl https://example.com` from a sandbox gets
  403. In both images (`/usr/bin/melissa-netbridge`). Details: `docs/agent-skills/agent-egress.md`.
- **App tools (2026-11-18):** `list_catalog`, `app_status` (read-only), `app_logs` (untrusted), `install_app`
  (Reversible), `uninstall_app` (Destructive) in `crates/hive`, over separate `AppRead`/`AppDeployer`
  traits. Generated secrets are never returned to agents; the owner reads them with
  `sudo melissa-queen app-credentials <app>`. `melissa-queen tool --wait <tool> [json]` runs a tool in the
  daemon and waits for its confirmation (`POST /api/tools/{name}`).
- **Cluster tools (2026-11-18):** `cluster_health` (read-only) in `crates/hive`, registered next to `comb_info`;
  verified in the headless VM through the queen's own credentials. `melissa-queen tool <name> [json]` runs one tool
  through the MCP session path (unattended policy, no waiting for confirmations) for operators and tests.
- **ACP sessions (2026-11-18):** long-lived agent sessions behind a protocol-neutral API (`crates/agent/src/session`:
  open, prompt, cancel, close, typed events, permission handler) implemented over ACP with the official Rust crate
  (`crates/agent/src/acp`). Built-in backend `grok-acp` (`grok --permission-mode default agent --no-leader stdio`,
  sandboxed) gets Melissa's MCP endpoint per session; its permission requests go through the tool policy and the
  confirmation inbox (never "always"). Verified on the laptop: comb_info through MCP, streaming answer, audit,
  graceful cancel and a second prompt in one session, and board cancel killing the sandbox. Replay tests with a
  recorded, scrubbed Grok transcript.
- **More session backends (2026-11-18):** `opencode-acp` (`opencode acp`, ACP flavor `opencode`: Melissa writes
  OpenCode's config: every tool asks, MCP without Code Mode, user config hidden) and `claude-session` (Claude Code
  driven natively over its stream-json protocol: no built-in tools, every permission prompt answered by
  Melissa's policy over `--permission-prompt-tool stdio`, interrupt for cancel, `--resume` with a Melissa-owned
  `~/.claude/projects`). Both sandboxed behind the egress proxy (learn mode: no new hosts; Claude now contacts
  only `api.anthropic.com`). Verified on the laptop for each: comb_info task, Queen + worker, policy-answered
  permissions (OpenCode shell → inbox → denied), cancel, second prompt, resume after a daemon restart. Replay
  tests from recorded, scrubbed transcripts. Queen default order: `grok-acp`, `claude-session`, `opencode-acp`.
  Details: `docs/agent-skills/acp-sessions.md`.
- **Queen loop (2026-11-18):** the Queen runs in `melissa-queen` (`melissa_agent::queen`): one lazily opened,
  long-lived session from an ordered backend list (`[queen] backends`, default `grok-acp`), one turn at a time,
  cancel, `session_lost` + new session when the agent dies, the shipped system prompt
  (`crates/queen/prompts/queen.md`) as the first message's preamble. Since the hive-model change (2026-11-18)
  the Queen directs persistent, named **bees** (Queen-only tools `create_bee`, `give_bee_job`, `bee_status`,
  `list_bees`, `stop_bee`, `message_bee`, `reassign_cell`); each bee is a conversation like the Queen's (own
  session store, sandbox, scope, transcript), at most `max_bees` working at once, job time limits, all audited.
  Typed event stream + JSONL transcript; JSON API `/api/queen/*`, `/api/bees/*`, `/api/cells/*`,
  `/api/confirmations`; CLI `melissa-queen chat|ask [--bee]|confirm|bee|cell`. Context
  survives daemon restarts and agent crashes through `session/resume` with a Melissa-owned Grok session store
  (verified), else a transcript summary. Verified live on the laptop (comb_info + a grok worker in 23 s, chat
  context, cancel, resume). Details: `docs/agent-skills/queen-loop.md`. Since 2026-11-18 also on
  `claude-session` and `opencode-acp` (see above). Next: chat UI (owner's design), per-bee budgets.
- **Cells and ownership (2026-11-18, owner: "agents change only what belongs to them"; hive model):** every
  installed app is a cell owned by one bee (`melissa.io/owner-bee`, plus `melissa.io/cell`, `melissa.io/comb`,
  assigned-by/at); every task has a scope (user / Queen of a comb / bee / nothing). One check in the tool
  registry, before the label policy, for every tool that declares a target: a bee on another bee's (or an
  unassigned) cell → refused + `tool.refused`; the Queen on a bee's cell → allowed, and destructive
  confirmations name the bee; the Queen on an unassigned cell → confirmation. Every install names its bee.
  Reassign: the Queen's `reassign_cell` (always the user's confirmation) or the user's
  `melissa-queen cell reassign`; admission lets the owner change only with a new assignment record. Old
  owner labels count as unassigned. Verified with unit tests (fake cluster, replay agents) and a live laptop
  run (Queen creates bee Ada, gives her a comb_info job, the user chats with Ada, resume after restart); the
  CEL rules still need a VM run. Details: `docs/agent-skills/cells-and-ownership.md`. Next: the same
  `target()` on update/restart/scale/stop tools as they land; agent-built apps and backups as cell kinds.
- **Next steps (ideas reviewed against the earlier draft, adopt now):**
  - Typed event stream per task (text, tool call, confirmation needed, usage, done, error) using each CLI's JSON
    streaming mode; push to the UI over SSE (htmx SSE extension, vendored).
  - Per-task budgets (wall clock, tokens, tool calls); pause and notify instead of failing silently. Child tasks get
    at most the parent's permissions and remaining budget.
  - Narrow tool API, v1: `list_apps`, `app_status`, `install_app(manifest)`, `update_app`, `scale_app`, `backup_now`,
    `list_backups`, `restore` (confirm), `remove_app` (confirm), `read_logs`, `cluster_health`, `ask_human`.
    Every tool is labelled (reads private data, reads untrusted input, can send data out, side effect:
    none/reversible/destructive); policy keys off labels. Destructive always needs confirmation. An unattended
    agent may not hold private data + untrusted input + an outbound channel at once. Once a task has read
    untrusted input, risky calls need confirmation. Denied tools are hidden from the agent.
  - Confirmations as objects in an inbox (UI component), approve/deny, all audited.
  - Audit records get an id, a hash chain (`prev_hash`) and an argument hash, plus `melissa audit verify`; a
    separate user owns the file so agents cannot write it.
  - Sandbox agent CLIs (done with bubblewrap and deny-by-default egress, see Sandbox and Egress above).
    Still to do: show egress denials in the UI (owner's design), per-task egress budgets.
  - Agents never see secrets; tools receive credentials by reference.
- **The Queen is the head agent (owner, 2026-11-18):** a long-lived LLM session (like a chat bot) that the user talks
  to; it plans and starts sandboxed **worker agents** for concrete jobs, each with a narrower tool set and budget, never
  more than the Queen's own permissions. The `melissa-queen` daemon hosts the Queen, the workers and the web UI, and
  enforces policy, confirmations and the audit log regardless of what any agent says. Queen backend: a configurable,
  ordered list of subscription backends (Claude first). No local LLMs on weak hardware such as the dev laptop
  unless a very small model proves useful.
- **The box ships empty (owner, 2026-11-18):** the image holds only what the web UI and agents need, plus k3s (which
  stays in the image). Everything else (apps, their config) is set up through agents after first boot; a few
  preinstalled things are fine during development.
- **Runtime app installs (owner, 2026-11-18):** apps are pulled live at runtime by agents that run in sandboxes.
  Split of duties: the sandboxed agent decides and calls tools (`install_app`, `update_app`, ...); the queen validates
  against the catalog manifest, applies the policy and creates the k3s objects; k3s/containerd pulls the images on
  the node. Agents get no cluster credentials and no general network access (model endpoint + Melissa tools only).
  Apps run in k3s, one namespace each, with their own volumes and network policy. So: agent sandboxing moves up.
- **Agents build apps in their own sandboxes (owner, 2026-11-18):** sub-agents may create apps (not only install
  catalog apps), each in its own sandboxed environment; **Nix** is a candidate tool for those per-agent environments
  (reproducible toolchains). Agents also do cleanup and maintenance (prune images, logs, finished workspaces;
  updates), with destructive steps behind confirmations.
- **After the demo: ephemeral worker bees and typed reports (owner idea, 2026-11-18; research: Hermes Agent study,
  dual-LLM / plan-then-execute / CaMeL patterns).** Three tiers: Queen (talks to the user, stays clean) → persistent
  Bee (owns cells, stays clean) → **ephemeral worker** (spawned by a Bee for one "dirty" job such as reading logs; a
  leaf: can't spawn, can't ask the user, never resumed after reading untrusted content; read-only scope; its own
  sandbox; destroyed afterwards, so its taint dies with it). Rules to adopt:
  - Reports have two parts: a **harness part from the audit log** (tools called, targets, effects, egress hosts,
    whether untrusted content was read; the only source of "what I did") and a **worker part validated against a
    schema** (enums, numbers, ids that must match real cells). One retry, then the report is marked invalid.
  - **Validated typed fields don't taint** the reader (Bee/Queen); free-text `notes` are capped, marked untrusted,
    and taint whoever reads them (shown to the owner instead). Free text never becomes a tool argument.
  - Workers never raise confirmations; they report `needs_action` and the clean Bee decides and asks.
  - Limits: depth 2 (Queen → Bee → worker), 2–3 workers per Bee plus a hive-wide cap, per-worker budgets; scrub
    secrets from worker output; summary size budget with overflow to a file.
  - No memory/skill writes from a tainted context; memory loaded as a frozen snapshot per session, with provenance
    per entry. No LLM-rated "smart" approvals (they can be injected).
  - Open: should worker report schemas be a fixed, human-reviewed library (like UI components)? Leaning yes.
    Should only the owner see a worker's `notes`? Later: chat-gateway pairing codes (outward-facing, needs the
    owner's yes); a credential-injecting egress proxy (needs TLS interception, which our proxy avoids by design).
- **Isolation with explicit links (owner, 2026-11-18):** apps and agents are isolated by default but may talk to each
  other when needed, or via the Queen. Design: agent to agent only through the Queen (brokered, audited, treated as
  data); app to app blocked by default, links declared in manifests and opened by the queen after approval
  (NetworkPolicy); agent to app only through tools; app internet access by per-manifest allowlist. Honest claim:
  "strong, layered and tested", never "unbreakable" (shared kernel). Hardening milestone: seccomp + cgroup limits +
  per-agent UIDs for sandboxes; default-deny NetworkPolicy, quotas, restricted Pod Security and user namespaces for
  apps; gVisor/microVM runtime for agent-built apps; an adversarial escape test suite gating image updates.
- **Reference:** T3 Code (github.com/pingdotgg/t3code) is a useful reference for multi-agent, many-backend UX. It is currently published under the MIT license — re-verify the license and notice requirements before reusing any code; otherwise treat it as inspiration only.

## 6. Web UI

- Headless OS, so the UI is a web app served by the bee. Stack: **Rust server-side templating (axum + maud, or askama) + htmx**, with htmx and CSS embedded in the binary via **rust-embed** (no CDN, works offline). Optional Alpine.js for tiny client state, Pico.css for styling. Pin and vendor all assets (see `crates/web/assets`).
- Rationale: light, stable, little churn, nothing that needs constant updating; easy for contributors to extend.
- **Fixed component library + app manifests.** The UI is built only from a reviewed set of components (cards, tables, forms, logs, status badges, confirm dialogs). Apps declare their needs in manifests (name, icon, ports, storage, config fields, health checks). **AI agents must NEVER generate custom UI elements.** They only select components and fill manifests. New components are human-reviewed code.
- Auth: local accounts + passkeys later; sessions with CSRF protection from day one. Until login exists the queen
  binds to loopback only, mutating requests must be same-origin (`Sec-Fetch-Site`/`Origin`), and a strict CSP
  (no inline script/style) is set. With login: `__Host-` cookies (`HttpOnly`, `Secure`, `SameSite=Strict`), CSRF
  tokens, Argon2id passwords, revocable sessions, and a one-time setup code shown on the console to claim a new bee.
- Agent and model output is untrusted. Agent prose is Markdown (CommonMark + GFM tables, strikethrough, task lists)
  rendered by one fixed component (`components::markdown`, owner-approved 2026-11-19): raw HTML shows as text,
  links only to http/https/mailto (new tab, `noopener noreferrer nofollow`), bare URLs linked, images never loaded.
  Logs and tool output stay escaped plain text.
- Later: problem+json error codes, a build-id header with an "updated, reload" banner, SSE for live updates.

- **UI direction (owner, 2026-11-18):** simple, like a chat bot. **Home = the chat with the Queen, with a compact
  preview of the apps' state** (honeycomb strip: what runs, what's installing, disk warnings). Approvals appear inline
  in the chat and in a "Waiting for you" list. Secondary screens: the Hive (apps as honeycomb cells, bees with
  resource bars), a worker's sandbox view (plan, live output, what it can reach, upkeep log). Concept mockups:
  claude.ai artifact "Melissa UI concepts" (private to the owner). The owner approved building them for the
  pre-alpha demo.
- **Status (2026-11-18):** built in `crates/web` (branch `t3/chat-home-hive-ui`, on top of the hive-model rename):
  home = chat with the Queen (app strip, replies as Markdown (since 2026-11-19), "what I did" rows, helper rows that link to
  the helper, inline approval cards, composer with backend line and Stop), `/hive` (apps as honeycomb cells with
  "Looked after by <bee>", "Add an app" into the chat, device cards), `/approvals`, and `/bees/{bee}` (chat with one
  helper; listed under Conversations in the rail); the task dashboard moved to `/tasks`. Live updates over SSE from
  the conversations' event logs (htmx SSE extension, vendored). Fonts Atkinson Hyperlegible Next and Bricolage
  Grotesque vendored (OFL). The UI says "helper" for a bee and "app" for a cell. Details:
  [htmx-component.md](agent-skills/htmx-component.md). Backend/model switch (2026-11-19): "Runs on Grok ▾" in the
  composer status of the Queen's and each helper's chat; API `/api/queen/backend(s)`, `/api/bees/{bee}/backend(s)`,
  CLI `melissa-queen backend list|use`; see [queen-loop.md](agent-skills/queen-loop.md). Not yet: disk usage, upkeep line, several conversations with
  the Queen / New chat, chat history after a daemon restart (event logs are in memory; transcripts have it).

## 7. Language and code layout

Repository: private GitHub repo for now (owner approved 2026-11-18); public only with an explicit yes.

**Rust** is the primary language for everything (daemons, CLI, agent layer, UI server). Reasons: memory safety, strong types and the compiler as a guard rail make AI coding agents more reliable. Go (or other languages) only where truly needed, e.g. glue for the k3s ecosystem; none is planned.

Cargo workspace (skeleton exists, not yet built):

```
Cargo.toml          # workspace, lints (forbid unsafe, warn on unwrap)
crates/queen        # queen bee: coordinator, agent layer entrypoint
crates/comb         # per-device daemon (comb)
crates/web          # axum + maud UI, embedded htmx (rust-embed)
crates/agent        # backend trait, echo + CLI backends (claude, grok, opencode), task board, audit log
crates/hive         # k3s client (kube-rs, rustls) behind small traits, cluster + app tools, rendering
crates/catalog      # app manifest schema, validation, config resolution
# planned: crates/mesh (tailscale/headscale/netbird adapters)
manifests/          # app manifests (nextcloud; immich next)
image/              # Containerfile(s), bootc config
docs/
```
