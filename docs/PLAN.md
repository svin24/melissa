# Melissa — project plan

Status: draft v0. Agents may expand any section; keep decisions and open questions up to date.

## 1. Vision

Melissa is an open source, clustered, agent-run, immutable self-hosting OS. A user installs it on one or more
machines, and an AI agent runs the infrastructure: setting up any app the user asks for, updating, backing up,
and healing.

Naming:
- **Agent** — a node running Melissa. Each agent can run its own local agents.
- **Cluster** — the cluster of agents.
- **Lead agent** — the master agent that coordinates the cluster (scheduling, upgrades, policy). Agents stay useful without it.

Agent backends are pluggable. An agent may be a "dumb box" with no LLM at all, or use external LLM subscriptions
(Grok, Claude, OpenCode with models such as Gemma). Local models are optional.

A VPS can join as an agent for: offsite backups (restic or Kopia), public ingress (important behind CGNAT such as
Starlink), VPN exit, seedbox. The VPS is **kept out of the control plane**: it is a worker/edge, never holds
cluster-admin credentials or the lead agent.

Goals: boring and reliable, immutable and atomically updatable, works on a LAN without internet for the UI,
easy for others to fork and build on.
Non-goals (for now): a general-purpose desktop distro, a custom UI generated by AI, supporting every hardware type.

## 1b. Agent model

Binding spec: [AGENT-MODEL.md](AGENT-MODEL.md) (owner, 2026-11-18), diagram `agent-model.svg`. Fleet > Cluster > Device
(one machine, one lead agent each; the primary device's lead agent has the final say) > Agents (workers) > Workspaces (one
agent's area of responsibility) > Services (workloads). Terms are internal roles; display names are chosen by the user or by
a lead agent. Until 2026-11-19 these were bee terms (hive, comb, queen, bee, cell, apiary); renamed by the owner so
contributors aren't confused, with a migration for existing installs (DECISIONS.md, 2026-11-19).
**Status (2026-11-18):** the code follows the model on one device: `crates/device`, device/agent ids, persistent named
agents with their own resumable sessions, workspaces owned by agents (namespace labels + admission), reassign only by the
lead agent with the user's yes or by the user, user chat with any agent, agent-to-agent only via the lead agent. Mapping table in
AGENT-MODEL.md; details in `docs/agent-skills/workspaces-and-ownership.md` and `lead-loop.md`. Multi-device is M3.

## 2. Packaging: container first (host-first)

> **Direction change (2026-11-19, owner):** Melissa runs **on an existing Linux host** first. The supported way is a
> **rootful podman container** started by systemd (Quadlet). A **Nix-packaged service** (flake, systemd units) is a
> parallel track under `packaging/nix/`. The bootc OS images, VM tooling and release disk are removed from the
> repo and preserved at git tag `bootc-archive-2026-11-19` (see "Reference distro (paused)" below).

- **Layout:** `packaging/common/` holds the host-agnostic system files every packaging installs (lead agent and k3s
  units, kubeconfig helper, sysusers/tmpfiles, k3s config and manifests, polkit rule, `melissa-setup`,
  `k3s-prepare`, `k3s.lock`), paths mirroring the install layout (`packaging/common/README.md`).
  `packaging/container/` is the container packaging; `packaging/nix/` the Nix one.
- **Container image** (`packaging/container/Containerfile`): `FROM registry.fedoraproject.org/fedora:45`, systemd as
  PID 1. Stages: Rust build (+ license report), k3s fetch (pinned and sha256-checked from `k3s.lock`), runtime with
  only what Melissa needs (`packages.txt`: systemd, bubblewrap, nftables, iptables-nft, polkit, curl, ...). No
  kernel, bootloader, bootc, sshd, NetworkManager, chrony, firewalld or Tailscale: **the host provides networking,
  time, SSH and Tailscale.** logind and the sleep targets are masked (the container must never handle the host's
  power keys or lid). An image lint step checks what must and must not be in it. `/usr/lib/melissa/release`
  carries version, revision and `MELISSA_RUNTIME=container`.
- **Install** (`packaging/container/install.sh`, root): preflight (podman ≥ 5, cgroup v2 controllers, br_netfilter
  and overlay, free ports, bridge subnet vs k3s's), the Quadlet `/etc/containers/systemd/melissa.container`
  (`systemctl start|stop|status melissa`, starts at boot), the kubelet's host sysctls written openly to
  `/etc/sysctl.d/90-melissa-kubelet.conf` with a notice (restored by `uninstall.sh`). Data: the `melissa-var`
  volume (`/var`, with `/etc/melissa` and k3s's node password symlinked onto it); the container is recreated
  from the image at every start. `uninstall.sh` keeps the volume unless `--purge`.
- **Network:** podman's default bridge. UI: host `127.0.0.1:8080` → container `:8081` → lead agent on its own
  loopback, nftables-filtered so pods can't reach it. Apps: NodePorts 30000–30079 published on `BIND`
  (127.0.0.1 by default; e.g. the host's Tailscale address). Remote use: `ssh -L` or `tailscale serve` (the UI has
  no login yet). `[apps] addresses` must be covered by `BIND`: install.sh refuses a mismatch and rewrites a stale
  key on reinstall; the app tools also try each address at run time and drop dead ones from links
  (DECISIONS 2026-11-20).
- **Updates:** Quadlet `AutoUpdate=` with `podman-auto-update.timer` (daily), plus Settings → Updates
  Check/Apply/Roll back through a host helper (`melissa-host-update`) that the lead agent triggers with fixed-name
  request files in a bind-mounted directory; the previous image is kept for a rollback (DECISIONS 2026-11-19).
- **Rootless podman: unsupported** (it worked with the earlier image; needs cpuset delegation and pasta; no longer
  tested). `scripts/container-run.sh` keeps it for experiments and is the dev/test driver (`build`, `smoke`).
- **Update distribution:** images are published first to `ghcr.io` (not yet; nothing is published without the
  owner's yes). Later a Cloudflare-fronted or custom registry domain; clients migrate through `registries.conf`
  mirrors. Sign images (cosign) before any public release.
- **BuildStream:** a cleaner reproducible build is "later later". Not before the product works.

### 2b. Nix service (host-first track 2)

Kept separate from the container-first text above on purpose (two tracks, two authors).

- **Flake outputs (2026-11-19):** `packages.<system>.melissa` (workspace from `Cargo.lock`, UI embedded),
  `nixosModules.melissa` (`services.melissa`), `checks.x86_64-linux.melissa-nixos` (NixOS VM test), and a
  prototype `melissa-host` bundle for other distributions with Nix. Details:
  `docs/agent-skills/nix-service.md`.
- **NixOS module:** the shared lead agent unit, tmpfiles, polkit rule, k3s config and manifests and helpers
  from `packaging/common/` (no copies; `packaging/nix/common.nix` names the root), nixpkgs' `services.k3s`
  (1.37) with the node IP pinned by the shared `k3s-node-ip` (also used by the container's `k3s-prepare`),
  UI on loopback, app ports 30000-30079 behind `apps.openFirewall`.
- **Agents on NixOS:** `services.melissa.agents.packages` (Nix-built claude/grok/opencode) is the documented
  way; Settings → Providers doesn't install agents on Nix installs. nix-ld stays on for CLIs installed by
  hand with `melissa-setup`.
- **Release file:** the package ships `lib/melissa/release` (`MELISSA_VERSION`, `MELISSA_REVISION`,
  `MELISSA_RUNTIME=nix`); the lead agent reads it through `MELISSA_RELEASE_FILE` (set by the module and the
  `melissa-host` drop-in; default `/usr/lib/melissa/release`).
- **Updates on NixOS** are the system's: `nix flake update` + `sudo nixos-rebuild switch`, rollback with
  `sudo nixos-rebuild switch --rollback` or the boot menu. Melissa never rebuilds the system itself.
  Settings → Updates shows the running version, these commands and no update buttons (Restart stays);
  provisional text, the owner reviews it (open question 62).
- **Other distributions:** `melissa-host` (root Nix profile as GC root, `melissa-host install` links units into
  `/etc`); k3s from the distribution. Not system-manager for now (Fedora unsupported upstream).

## 3. Cluster layer

- **Status (2026-11-19):** k3s v1.37.2 ships in the container image, pinned by sha256 in
  `packaging/common/usr/lib/melissa/k3s.lock`, airgap images in `/usr`, Traefik telemetry off, SELinux left to the
  host (k3s `selinux: false` inside). Smoke test passes rootful (node Ready, Traefik, policies, RBAC, NodePort, pods
  can't reach the UI). See docs/agent-skills/k3s-in-container.md. (Verified earlier in the bootc VM with
  k3s-selinux and SELinux enforcing; archived.)
- **Lead agent ↔ k3s (2026-11-18):** the lead agent talks to the API as ServiceAccount `melissa/melissa-server` with read-only
  RBAC (get/list/watch on nodes, namespaces, pods; no Secrets, no writes). A root oneshot
  (`melissa-kubeconfig.service`) writes its kubeconfig to `/run/melissa-kube` (root:`melissa-kube` 0640); the
  lead agent service has that group, does not wait for k3s at boot and re-reads the file on each cluster call.
  Client: kube-rs over rustls in `crates/cluster`.
- **App deploys (2026-11-19, replaces the 2026-11-18 catalog):** no catalog. Agents deploy any app from a
  JSON spec they write (`crates/appspec`: containers with pinned images, env, generated secrets, files, TCP/UDP
  ports, volumes, resources, probes, sidecars), rendered to Namespace `app-<name>` + RoleBinding + Secrets +
  PVCs + Deployment + Services + Traefik Ingress (`<app>.melissa.home.arpa` by default, `[apps] domain`) and
  server-side applied by a second identity, `melissa/melissa-apps`, whose writes admission policies pin to
  `app-*` workspace namespaces with Pod Security baseline, never privileged or on the host (no Secret reads
  anywhere). Every deploy and update is confirmed by the user with a summary of what runs. Tools: `deploy_app`,
  `update_app`, `list_apps`, `app_status`, `app_logs`, `app_exec`, `stop_app`, `start_app`, `uninstall_app`. The old
  catalog's Nextcloud keeps running and is converted to a stored spec at startup. Details:
  `docs/agent-skills/app-deploy.md`.
- **Orchestrator:** k3s (single binary, fits small boxes). Node labels describe roles (`melissa.io/role=storage|gpu|edge|gaming`, final label domain TBD).
- **App links (2026-11-19):** by default `http://<device address>:<port>`: an app's web port and each public
  TCP/UDP port get their own NodePort from 30000-30079 (`<app>-port` Service, recorded in `melissa.io/port` and
  `melissa.io/ports`), reachable on the LAN and over Tailscale with no DNS; the web UI builds links from the
  address the visitor used and shows other ports as `address:port (TCP|UDP)`. See DECISIONS.md.
- **Ingress:** wildcard `*.<domain>` (e.g. `nextcloud.<domain>`, `immich.<domain>`) via the k3s ingress controller, with automatic TLS (internal CA on LAN, ACME for public). Today an extra option for people with their own DNS (`dns_url`).
- **HA virtual IP:** kube-vip or keepalived for the control-plane/ingress address.
- **Storage:** Longhorn first (simple), Ceph (Rook) for larger clusters. Local-path for single-node M2.
- **Apps:** agents write Melissa's own app spec (JSON, see above and DECISIONS.md), rendered to plain
  objects; no Helm/kustomize, no catalog. Verified: Nextcloud (SQLite), a Minecraft server, plain web apps.
- **Gaming node (later):** KubeVirt with GPU passthrough (VFIO) running SteamOS/Windows VMs, streamed through Sunshine/Moonlight.

## 4. Networking and access

- **Mesh:** Tailscale with pre-auth keys by default; Headscale (self-hosted control server) or NetBird as alternatives. Abstract it behind a small Rust trait so the mesh is swappable.
- **Two access modes for remote use:**
  1. *Hosted relay with login* — user signs in to a hosted service that relays to their cluster (like T3 Connect with an auth provider such as Clerk). Easiest for non-technical users.
  2. *Bring your own Tailscale* — the user joins their own tailnet; no Melissa-run service involved.
- Public exposure goes through an edge agent (VPS) over the mesh, not by opening home router ports.
- The LAN UI must keep working with no internet.

## 5. Agent layer

- Multi-backend agent abstraction in Rust (a trait per backend, async streams): Claude (Opus 5.5), Grok, OpenCode (Gemma, etc.), later others. One interface for sessions, tool calls, streaming and cancellation.
- Agents act through a **narrow tool API** (install app, scale, back up, restore, update, inspect health), not raw root shells. Every mutating action is logged and, per policy, requires confirmation.
- Lead agent coordinates; each agent may run local agents scoped to that agent.
- **Status (2026-11-18):** `crates/agent` has the `Backend` trait, a built-in `echo` backend (no LLM), a CLI
  backend that drives `claude -p`, `grok -p` and `opencode run` (all verified working), a task board with
  cancel/timeout/output cap, and a JSONL audit log.
- **Tools (2026-11-18):** narrow tool API with label-based policy, confirmation store and audited calls
  (`crates/agent/src/tools`), served to agent CLIs over MCP (`crates/agent/src/mcp.rs`, `POST /mcp/<token>`).
  Claude runs with no built-in tools and only Melissa's (verified). First tool: `device_info`. The confirmation
  inbox needs UI (waiting for the owner's UI ideas); Grok and OpenCode get tools via ACP, Claude sessions via
  stream-json (below).
- **Sandbox (2026-11-18):** every agent CLI runs under bubblewrap by default (`crates/agent/src/sandbox.rs`):
  read-only `/usr` and `/etc`, private `/tmp`, empty read-only home with only the CLI's credential file(s), the
  task workdir as the only writable host path, own PID/user/IPC/UTS namespaces, no capabilities, dies with the
  lead agent's task. Verified with claude (incl. MCP tool calls), grok and opencode. Next: seccomp, Melissa-owned
  CLI logins.
- **Egress (2026-11-18):** deny-by-default network for every sandboxed agent (`crates/agent/src/egress`): own
  network namespace with loopback only and no resolver; `melissa-netbridge` inside forwards to per-sandbox Unix
  sockets served by the lead agent: an HTTPS `CONNECT` proxy with a per-backend host allowlist (DNS by the lead agent,
  non-public addresses refused, limits, every decision audited as `egress.allow|deny|error`) and an MCP-only
  endpoint (the rest of the lead agent's API is unreachable from agents). `network = "proxy"` (default) | `"learn"` |
  `"none"` | `"host"`, `allow = [...]` per backend; built-in allowlists found with learn mode. Verified live on
  the laptop: claude + device_info, grok-acp + device_info, opencode, and the lead agent with a worker, all under
  `proxy`, with telemetry (Datadog, Mixpanel, grok.com) denied; `curl https://example.com` from a sandbox gets
  403. In both images (`/usr/bin/melissa-netbridge`). Details: `docs/agent-skills/agent-egress.md`.
- **App tools (2026-11-18, deploy tools 2026-11-19):** `app_status`, `list_apps` (read-only), `app_logs`
  (untrusted), `deploy_app`/`update_app` (always confirmed), `uninstall_app` (Destructive) in `crates/cluster`, over separate `AppRead`/`AppDeployer`
  traits. Generated secrets are never returned to agents; the owner reads them with
  `sudo melissa-server app-credentials <app>`. `melissa-server tool --wait <tool> [json]` runs a tool in the
  daemon and waits for its confirmation (`POST /api/tools/{name}`).
- **`app_exec` (2026-11-20):** one command (argv, no implicit shell) in an app's running container over the
  Kubernetes exec API (kube-rs `ws`), e.g. a Minecraft console command (`rcon-cli op <player>`) without a
  restart. Only the owning agent or the lead agent (scope `Change`), always confirmed with the exact argv
  (Destructive), output untrusted (taints) and bounded (64 KiB per stream, 30 s default / 300 s max timeout).
  The audit line records who, app, argv, stdin length (not content), pod, container and exit code. RBAC: the
  per-app-namespace workload role gains `pods/exec` `get`+`create`; still no attach or port-forward.
- **Cluster tools (2026-11-18):** `cluster_health` (read-only) in `crates/cluster`, registered next to `device_info`;
  Verified in the headless VM (bootc, archived) and again in the rootful container (2026-11-19) through the lead agent's own credentials. `melissa-server tool <name> [json]` runs one tool
  through the MCP session path (unattended policy, no waiting for confirmations) for operators and tests.
- **Standing permissions (owner, 2026-11-20):** two owner-approved ways to answer confirmations ahead of time,
  both in `melissa_agent::tools::permissions` and checked in `ToolRegistry::confirm`, i.e. only *after* the scope
  and argument checks, so refusals ("not yours", bad arguments, an agent switching its own permission mode)
  stay refusals. (1) **Always allow**: a third button on every approval card (an agent's or the lead agent's
  request; never the user's own). It approves the call and saves a rule keyed on the asking principal (agent id,
  so renames keep it; the lead agent is its own principal) + tool name + target (the workspace, for targeted
  tools; untargeted tools such as an agent's `agent:execute` match only untargeted calls of that kind). Exact
  match only. Matching calls are approved without a prompt (audited `tool.auto_approved`, actor `rule`, detail
  `rule <id>`); pending ones the new rule matches are approved at once (`confirmation.auto_approved`). Rules are
  listed and removed in Settings → Permissions. (2) **No permission prompts** (Settings → Developer, off by
  default, confirm card to switch on): every confirmation is approved (actor `bypass`), all pending ones too;
  no banner on the pages (owner, 2026-11-20: it was switched on knowingly; Settings → Developer shows it). Both live in
  `$XDG_STATE_HOME/melissa/permissions.json` (0600, outside every sandbox); a broken file grants nothing.
  Agents have no tool for either: only the owner's UI and API (`/api/confirmations/{id}/always`,
  `/api/settings/permissions*`) change them, audited `permissions.rule_added|rule_removed|bypass`.
- **Scheduled jobs (owner, 2026-11-20):** "Ada: update all apps and the system, nightly at 3:00". A schedule gives
  one agent (by id, or the lead agent) a recurring instruction on a 5-field cron expression evaluated in the box's
  local time zone (croner on jiff; DST: a time in the skipped hour runs right after the gap, a repeated hour runs
  once). Saved in `$XDG_STATE_HOME/melissa/schedules.json` (0600); every change and run audited `schedule.*`.
  A Tokio task in the agent layer (`lead::schedules::Scheduler`) sleeps until the next due time (at most a
  minute) and sends the instruction as a turn of that agent's conversation (the lead agent's main chat, or the
  agent's own, waking a stopped agent), shown as the user message with a "Scheduled: <name>" label. Rules:
  **skip, not queue**, when the previous run is still going or the agent is busy (recorded "skipped": a queued run
  would start at a time nobody chose and pile up behind a stuck one; "Run now" is one click); a run missed while
  Melissa was down runs once on start if it was due less than an hour ago, else it is recorded "missed"; a
  confirmation no rule covers waits in "Waiting for you" as usual (no auto-deny), and a run still going after its
  time limit (default 60 min) is cancelled and recorded "timed out". The turn runs **unattended**: the lead
  agent's MCP session is marked unattended for its length, so what it may do alone is what the owner's "Always
  allow" rules cover. Agents propose schedules with the `schedule_job` tool (create/list/remove; an agent only for
  itself, the lead agent for any agent; another agent's schedules are refused "not yours"). Every create and
  remove through the tool needs the owner's yes, which **no "Always allow" rule can give** (the confirmation
  offers none, `Tool::owner_approval`): one approval must never become a standing licence to make more standing
  orders. The developer's No permission prompts **does** cover it, because it is the owner's explicit "approve
  everything" switch and already covers riskier calls; excluding schedules would make it lie. The owner manages
  schedules in Settings → Schedules (list with next and last run, on/off, Run now, remove, add/edit with presets)
  and `/api/schedules` without confirmations.
- **ACP sessions (2026-11-18):** long-lived agent sessions behind a protocol-neutral API (`crates/agent/src/session`:
  open, prompt, cancel, close, typed events, permission handler) implemented over ACP with the official Rust crate
  (`crates/agent/src/acp`). Built-in backend `grok-acp` (`grok --permission-mode default agent --no-leader stdio`,
  sandboxed) gets Melissa's MCP endpoint per session; its permission requests go through the tool policy and the
  confirmation inbox (never "always"). Verified on the laptop: device_info through MCP, streaming answer, audit,
  graceful cancel and a second prompt in one session, and board cancel killing the sandbox. Replay tests with a
  recorded, scrubbed Grok transcript.
- **More session backends (2026-11-18):** `opencode-acp` (`opencode acp`, ACP flavor `opencode`: Melissa writes
  OpenCode's config: every tool asks, MCP without Code Mode, user config hidden) and `claude-session` (Claude Code
  driven natively over its stream-json protocol: no built-in tools, every permission prompt answered by
  Melissa's policy over `--permission-prompt-tool stdio`, interrupt for cancel, `--resume` with a Melissa-owned
  `~/.claude/projects`). Both sandboxed behind the egress proxy (learn mode: no new hosts; Claude now contacts
  only `api.anthropic.com`). Verified on the laptop for each: device_info task, lead agent + worker, policy-answered
  permissions (OpenCode shell → inbox → denied), cancel, second prompt, resume after a daemon restart. Replay
  tests from recorded, scrubbed transcripts. Lead agent default order: `grok-acp`, `claude-session`, `opencode-acp`.
  Details: `docs/agent-skills/acp-sessions.md`.
- **Lead agent loop (2026-11-18):** the lead agent runs in `melissa-server` (`melissa_agent::lead`): one lazily opened,
  long-lived session from an ordered backend list (`[lead] backends`, default `grok-acp`), one turn at a time,
  cancel, `session_lost` + new session when the agent dies, the shipped system prompt
  (`crates/server/prompts/lead.md`) as the first message's preamble. Since the cluster-model change (2026-11-18)
  the lead agent directs persistent, named **agents** (Lead-only tools `create_agent`, `give_agent_job`, `agent_status`,
  `list_agents`, `stop_agent`, `message_agent`, `reassign_workspace`); each agent is a conversation like the lead agent's (own
  session store, sandbox, scope, transcript), at most `max_agents` working at once, job time limits, all audited.
  Typed event stream + JSONL transcript; JSON API `/api/lead/*`, `/api/agents/*`, `/api/workspaces/*`,
  `/api/confirmations`; CLI `melissa-server chat|ask [--agent]|confirm|agent|workspace`. Context
  survives daemon restarts and agent crashes through `session/resume` with a Melissa-owned Grok session store
  (verified), else a transcript summary. Verified live on the laptop (device_info + a grok worker in 23 s, chat
  context, cancel, resume). Details: `docs/agent-skills/lead-loop.md`. Since 2026-11-18 also on
  `claude-session` and `opencode-acp` (see above). Next: chat UI (owner's design), per-agent budgets.
- **Workspaces and ownership (2026-11-18, owner: "agents change only what belongs to them"; cluster model):** every
  installed app is a workspace owned by one agent (`melissa.io/owner-agent`, plus `melissa.io/workspace`, `melissa.io/device`,
  assigned-by/at); every task has a scope (user / Lead agent of a device / agent / nothing). One check in the tool
  registry, before the label policy, for every tool that declares a target: an agent on another agent's (or an
  unassigned) workspace → refused + `tool.refused`; the lead agent on an agent's workspace → allowed, and destructive
  confirmations name the agent; the lead agent on an unassigned workspace → confirmation. Every install names its agent.
  Reassign: the lead agent's `reassign_workspace` (always the user's confirmation) or the user's
  `melissa-server workspace reassign`; admission lets the owner change only with a new assignment record. Old
  owner labels count as unassigned. Verified with unit tests (fake cluster, replay agents) and a live laptop
  run (Lead agent creates agent Ada, gives her a device_info job, the user chats with Ada, resume after restart); the
  CEL rules still need a VM run. Details: `docs/agent-skills/workspaces-and-ownership.md`. Next: the same
  `target()` on update/restart/scale/stop tools as they land; agent-built apps and backups as workspace kinds.
- **Next steps (ideas reviewed against the earlier draft, adopt now):**
  - Typed event stream per task (text, tool call, confirmation needed, usage, done, error) using each CLI's JSON
    streaming mode; push to the UI over SSE (htmx SSE extension, vendored).
  - Per-task budgets (wall clock, tokens, tool calls); pause and notify instead of failing silently. Child tasks get
    at most the parent's permissions and remaining budget.
  - Narrow tool API, v1: `list_apps`, `app_status`, `install_app(manifest)`, `update_app`, `scale_app`, `backup_now`,
    `list_backups`, `restore` (confirm), `remove_app` (confirm), `read_logs`, `cluster_health`, `ask_human`.
    Every tool is labelled (reads private data, reads untrusted input, can send data out, side effect:
    none/reversible/destructive); policy keys off labels. Destructive always needs confirmation. An unattended
    agent may not hold private data + untrusted input + an outbound channel at once. Once a task has read
    untrusted input, risky calls need confirmation. Denied tools are hidden from the agent.
  - Confirmations as objects in an inbox (UI component), approve/deny, all audited.
  - Audit records get an id, a hash chain (`prev_hash`) and an argument hash, plus `melissa audit verify`; a
    separate user owns the file so agents cannot write it.
  - Sandbox agent CLIs (done with bubblewrap and deny-by-default egress, see Sandbox and Egress above).
    Still to do: show egress denials in the UI (owner's design), per-task egress budgets.
  - Agents never see secrets; tools receive credentials by reference.
- **The lead agent is the head agent (owner, 2026-11-18):** a long-lived LLM session (like a chat bot) that the user talks
  to; it plans and starts sandboxed **worker agents** for concrete jobs, each with a narrower tool set and budget, never
  more than the lead agent's own permissions. The `melissa-server` daemon hosts the lead agent, the workers and the web UI, and
  enforces policy, confirmations and the audit log regardless of what any agent says. Lead agent backend: a configurable,
  ordered list of subscription backends (Claude first). No local LLMs on weak hardware such as the dev laptop
  unless a very small model proves useful.
- **The box ships empty (owner, 2026-11-18):** the image holds only what the web UI and agents need, plus k3s (which
  stays in the image). Everything else (apps, their config) is set up through agents after first boot; a few
  preinstalled things are fine during development.
- **Runtime app installs (owner, 2026-11-18):** apps are pulled live at runtime by agents that run in sandboxes.
  Split of duties: the sandboxed agent decides and calls tools (`deploy_app`, `update_app`, ...); the server validates
  the agent's spec, applies the policy (the user confirms every deploy) and creates the k3s objects; k3s/containerd pulls the images on
  the node. Agents get no cluster credentials and no general network access (model endpoint + Melissa tools only).
  Apps run in k3s, one namespace each, with their own volumes and network policy. So: agent sandboxing moves up.
- **Agents build apps in their own sandboxes (owner, 2026-11-18):** sub-agents may create apps (not only install
  catalog apps), each in its own sandboxed environment; **Nix** is a candidate tool for those per-agent environments
  (reproducible toolchains). Agents also do cleanup and maintenance (prune images, logs, finished workspaces;
  updates), with destructive steps behind confirmations.
- **After the demo: ephemeral worker agents and typed reports (owner idea, 2026-11-18; research: Hermes Agent study,
  dual-LLM / plan-then-execute / CaMeL patterns).** Three tiers: lead agent (talks to the user, stays clean) → persistent
  Agent (owns workspaces, stays clean) → **ephemeral worker** (spawned by a Agent for one "dirty" job such as reading logs; a
  leaf: can't spawn, can't ask the user, never resumed after reading untrusted content; read-only scope; its own
  sandbox; destroyed afterwards, so its taint dies with it). Rules to adopt:
  - Reports have two parts: a **harness part from the audit log** (tools called, targets, effects, egress hosts,
    whether untrusted content was read; the only source of "what I did") and a **worker part validated against a
    schema** (enums, numbers, ids that must match real workspaces). One retry, then the report is marked invalid.
  - **Validated typed fields don't taint** the reader (Agent/Lead); free-text `notes` are capped, marked untrusted,
    and taint whoever reads them (shown to the owner instead). Free text never becomes a tool argument.
  - Workers never raise confirmations; they report `needs_action` and the clean Agent decides and asks.
  - Limits: depth 2 (Lead agent → Agent → worker), 2–3 workers per Agent plus a cluster-wide cap, per-worker budgets; scrub
    secrets from worker output; summary size budget with overflow to a file.
  - No memory/skill writes from a tainted context; memory loaded as a frozen snapshot per session, with provenance
    per entry. No LLM-rated "smart" approvals (they can be injected).
  - Open: should worker report schemas be a fixed, human-reviewed library (like UI components)? Leaning yes.
    Should only the owner see a worker's `notes`? Later: chat-gateway pairing codes (outward-facing, needs the
    owner's yes); a credential-injecting egress proxy (needs TLS interception, which our proxy avoids by design).
- **Isolation with explicit links (owner, 2026-11-18):** apps and agents are isolated by default but may talk to each
  other when needed, or via the lead agent. Design: agent to agent only through the lead agent (brokered, audited, treated as
  data); app to app blocked by default, links declared in manifests and opened by the lead agent after approval
  (NetworkPolicy); agent to app only through tools; app internet access by per-manifest allowlist. Honest claim:
  "strong, layered and tested", never "unbreakable" (shared kernel). Hardening milestone: seccomp + cgroup limits +
  per-agent UIDs for sandboxes; default-deny NetworkPolicy, quotas, restricted Pod Security and user namespaces for
  apps; gVisor/microVM runtime for agent-built apps; an adversarial escape test suite gating image updates.
- **Reference:** T3 Code (github.com/pingdotgg/t3code) is a useful reference for multi-agent, many-backend UX. It is currently published under the MIT license — re-verify the license and notice requirements before reusing any code; otherwise treat it as inspiration only.

## 6. Web UI

- Headless OS, so the UI is a web app served by the agent. Stack: **Rust server-side templating (axum + maud, or askama) + htmx**, with htmx and CSS embedded in the binary via **rust-embed** (no CDN, works offline). Optional Alpine.js for tiny client state, Pico.css for styling. Pin and vendor all assets (see `crates/web/assets`).
- Rationale: light, stable, little churn, nothing that needs constant updating; easy for contributors to extend.
- **Fixed component library + app manifests.** The UI is built only from a reviewed set of components (cards, tables, forms, logs, status badges, confirm dialogs). Apps declare their needs in manifests (name, icon, ports, storage, config fields, health checks). **AI agents must NEVER generate custom UI elements.** They only select components and fill manifests. New components are human-reviewed code.
- Auth: local accounts + passkeys later; sessions with CSRF protection from day one. Until login exists the lead agent
  binds to loopback only, mutating requests must be same-origin (`Sec-Fetch-Site`/`Origin`), and a strict CSP
  (no inline script/style) is set. With login: `__Host-` cookies (`HttpOnly`, `Secure`, `SameSite=Strict`), CSRF
  tokens, Argon2id passwords, revocable sessions, and a one-time setup code shown on the console to claim a new agent.
- Agent and model output is untrusted. Agent prose is Markdown (CommonMark + GFM tables, strikethrough, task lists)
  rendered by one fixed component (`components::markdown`, owner-approved 2026-11-19): raw HTML shows as text,
  links only to http/https/mailto (new tab, `noopener noreferrer nofollow`), bare URLs linked, images never loaded.
  Logs and tool output stay escaped plain text.
- Later: problem+json error codes, a build-id header with an "updated, reload" banner, SSE for live updates.

- **UI direction (owner, 2026-11-18):** simple, like a chat bot. **Home = the chat with the lead agent, with a compact
  preview of the apps' state** (app_grid strip: what runs, what's installing, disk warnings). Approvals appear inline
  in the chat and in a "Waiting for you" list. A helper's approval shows inline in its own chat and also in the lead
  agent's chat ("Ada asks: …"), and stays there across a new chat while it waits; deciding it anywhere updates all
  three (2026-11-20). Secondary screens: the Cluster (apps as app_grid workspaces, agents with
  resource bars), a worker's sandbox view (plan, live output, what it can reach, upkeep log). Concept mockups:
  claude.ai artifact "Melissa UI concepts" (private to the owner). The owner approved building them for the
  pre-alpha demo.
- **Status (2026-11-18):** built in `crates/web` (branch `t3/chat-home-cluster-ui`, on top of the cluster-model rename):
  home = chat with the lead agent (app strip, replies as Markdown (since 2026-11-19), "what I did" rows, helper rows that link to

  with its text (CSS `field-sizing`, a few lines of melissa.js where missing; no resize handle), and files go with a
  message (paperclip, paste, drop; chips with remove before sending; thumbnails and download chips in the chat).
  Files: `melissa_agent::attachments` (20 MiB per file, 50 MiB and 10 files per message; type sniffed from the bytes;
  stored under random names in `<state>/lead/attachments`, kept in the transcript's events; served only by

  image blocks (Claude; ACP agents that advertise `image`), PDFs as document blocks (Claude); everything else, and

  Not yet: disk usage, upkeep line, several conversations with
  the lead agent / New chat, chat history after a daemon restart (event logs are in memory; transcripts have it).
- **Voice input (2026-11-20, owner decision; DECISIONS):** Settings → Voice turns on a mic in the chat composer
  (off by default; `voice_input` in `ui.toml`). Speech becomes text **on the device**: the browser records and
  sends a 16 kHz WAV to `POST /ui/voice/transcribe`, the server runs whisper.cpp's `whisper-cli` (separate
  process; `crates/voice`), and the text lands in the message box to edit, never sent by itself. Clips are never
  stored. **Third-party network call (documented per AGENTS.md):** turning voice input on downloads the speech
  model once from Hugging Face, `https://huggingface.co/ggerganov/whisper.cpp/resolve/5359861c…/ggml-base.bin`

  the device or owner is sent (User-Agent `melissa`). The download is audited; Settings shows its progress and
  can delete the model while voice input is off. whisper.cpp comes from the packaging (container image stage,
  pinned in `packaging/container/whisper.lock`; Nix `services.melissa.voice.package`).
