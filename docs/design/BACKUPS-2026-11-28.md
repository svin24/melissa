# Backups (2026-11-28)

Status: core built (`crates/backup`, the app spec's `backup` field, the root unit). Not built yet: the
drive helper (mounting a drive the owner picks), the Settings UI, the first-run "restore this device"
flow. PLAN Q112 holds the open items.

## Decisions

Owner (fixed):
- Back up Melissa's own state **and** every app's data.
- Target: a drive the owner picks. For the core it is a directory; the mount comes later.
- Encryption optional and recommended (on by default).
- Weekly by default; configurable (a day and hour, daily, or off).
- Consistency is app-aware: a dump where the app's method is known; for an unknown app the agent
  researches and proposes a hook; otherwise the app is stopped briefly.

Engineering (fixed):
- Engine: **restic**, a pinned prebuilt static binary in the image (`packaging/container/restic.lock`,
  0.20.0, sha256 per arch and of the LICENSE, checked in the Containerfile like k3s and gVisor). Driven
  from Rust with `--json` behind `BackupEngine`, so rustic_core can replace it later on the same
  repository format. Relied on: `--insecure-no-password` and `backup --stdin-from-command` (restic
  0.17.0), exit code 12 for a wrong password (0.17.1), JSON `prune` output (0.20.0, not required).
- Unencrypted mode is restic with `--insecure-no-password`. Encrypted mode uses a generated recovery
  key, shown to the owner once; a root-only copy stays on the device for unattended runs.

## Architecture

```
 server (user melissa)                    root: melissa-backup.service            drive
 ─────────────────────                    ────────────────────────────            ─────
 Requester::ask ──► backup-request/  ──►  .path unit starts the service  ──►  <target>/
   run, init, ack-key,                     request::take (removes all)          melissa-backup.json (marker)
   restore-<app>[@t],                      Device::handle / Device::unit        repo/ (restic)
   config.json (checked by root)           marker::check_target before writes
 Requester::status ◄── backup-status/ ◄──  status.json (0640 root:melissa)
                       recovery-key.txt    (until ack-key)
                                          .timer hourly: Schedule::is_due → Device::backup
```

Crate `crates/backup` (`#![forbid(unsafe_code)]`, thiserror):

| module | what |
|---|---|
| `config` | `config.json` (version 1, atomic 0600): target, encrypted, repo id, schedule, retention; `ConfigRequest` (what the server may change) |
| `status` | `status.json` (version 1) the server reads; the one-time recovery key file |
| `request` | fixed-name request files, the server's `Requester`, root's `take` |
| `marker` | the drive's marker and the checks before init and before every write |
| `key` | the recovery key: 160 bits, Crockford base32, 8 groups of 4 + 1 check group |
| `engine` | `BackupEngine` trait and `Restic` |
| `inventory` | Melissa's state paths (lists shared with the factory reset) |
| `k3s` | the raw datastore snapshot (sqlite `VACUUM INTO`) and its same-version placement |
| `apps` | per-app export, `Cluster` trait, `Kubectl` (admin kubeconfig) |
| `run` | `Device`: init, adopt, backup, retention, restore one app, whole-device parts, the unit |

`melissa-server backup unit|status|now|setup|adopt|snapshots|restore-app` is the root CLI
(`crates/server/src/backup.rs`).

## Privilege split

Everything that reads data or writes the drive runs as **root** in `melissa-backup.service` (container
image): Melissa's state is the `melissa` user's, k3s's datastore and TLS keys are root's, app volumes
belong to whatever uid the app runs as, and Secret values need k3s's admin kubeconfig. The server
(user `melissa`) does two things only:

1. leaves **requests**: empty files with fixed names (`run`, `init`, `ack-key`, `restore-<app>`,
   `restore-<app>@<unix time>`) or `config.json` (target, encryption, schedule, retention;
   `deny_unknown_fields`, 16 KiB). Root removes every file it finds and acts only on names it knows;
   a target must be a plain absolute path **below `/run/melissa-backup`** (where the drive helper will
   mount drives), so the server can't point root's writes anywhere else. Root by hand
   (`melissa-server backup setup <dir>`) may use any directory;
2. reads **status**: `status.json` and, once, `recovery-key.txt` in `backup-status/` (root:melissa
   0750, files 0640).

No agent tool reaches either, and the code that reads Secret values (`apps::Kubectl::secrets`) only
runs in the root unit. The dump and restore commands of an app's hook run inside that app's own
container through `kubectl exec` (the app's privileges, not root's); the user approved them with the
spec (the confirmation shows `backup: ...`).

Directories (tmpfiles `melissa-container.conf`): `/var/lib/melissa-container/backup` (root 0700:
`config.json`, `key`, `lock`, `staging/`), `backup-status` (root:melissa 0750), `backup-request`
(root:melissa 0770). A factory reset removes the first two and empties the third; the backups on the
drive stay, and the owner's recovery key opens them.

## What is backed up

One restic snapshot per item; every snapshot of a run gets the same `--time` (the run's start, UTC),
`--host melissa` (the same on every device, so a new device sees its predecessor's backups; no real
host name on the drive). Retention groups by host and tags, so each item keeps its own history.

| item (tags) | contents |
|---|---|
| `item:state` | `BACKUP_STATE` = the factory reset's swept directories (`/var/lib/melissa`, `etc-melissa`) minus `BACKUP_EXCLUDE`: `tmp`, the voice model, home caches (`.cache`, `.npm`), `server.toml` (the install's), `providers.toml.broken`, `cluster.toml` and the cluster tokens/requests. Tailscale's node key, k3s and the cluster identity are in `BACKUP_ELSEWHERE`. A test makes every reset path either backed up or listed there. |
| `item:k3s` | `server/db/state.db` via `sqlite3 ... "VACUUM INTO"` (consistent while k3s runs, WAL included), `server/token`, `server/tls/`, `server/cred/` (with `encryption-config.json` for Secrets at rest), and `k3s-version`. For a same-version rollback only. |
| `app:<name>` `part:files` | `app.json` (spec annotation, workspace labels, ownership annotations, replicas, mode, volumes with their path, volumes left out), `secrets.json` (the app's generated Secrets, base64), and each volume's directory, found through PVC → PV → `hostPath`/`local` path, which must be under `/var/lib/rancher/k3s/storage` |
| `app:<name>` `part:dump` | the hook's dump (`--stdin-from-command`, `kubectl exec` into the container; restic fails the snapshot when the command exits non-zero) |

### App hooks (`backup` in the app spec)

`{mode: dump|stop|live|skip, dump?: {container, command, file}, restore?: {container, command, stdin},
exclude?: ["<volume>" | "<volume>/<path>"]}`, validated with the spec (containers and volumes exist,
argv limits as `command`, plain file names and paths, `restore.stdin == dump.file`, `dump` only with
mode dump). No field: `stop`. A stopped app (replicas 0) is copied as it is. The deploy path answers a
spec without the field with a suggestion from a small catalogue (`known_dumps()`): postgres
(`pg_dumpall --clean --if-exists` / `psql`), mariadb and mysql (`--all-databases --single-transaction`),
redis/valkey (BGSAVE, wait, print `dump.rdb`; no restore hook: the copied file is loaded at start), and
a SQLite `.backup`/`.restore` template. Agents are told to research other apps' methods
(docs/agent-skills/app-deploy.md, "Backups").

## Safety checks

- **Marker.** `<target>/melissa-backup.json` `{format, repo_id, created_at, encrypted, about}` next to
  `repo/`. Before every write (backup, forget) the target must be a real directory (not a symlink)
  with a marker naming the repository id in root's config and restic's `config` file; `open` also asks
  restic for the repository id (which proves the key). An unplugged drive's empty mountpoint, a
  different drive, or a newer marker format are refused, and nothing is written. Retention checks the
  marker once more right before `forget --prune`.
- **Init** only into an empty directory (`lost+found` allowed).
- **Config and status** are versioned; a newer format is refused, never half read. Writes are atomic
  (temp file, fsync, rename, fsync dir), never through a symlink. (No shared helper existed yet;
  `fsutil` is small and local.)
- **One run at a time**: a lock file in the config directory.
- restic runs with a cleared environment, `--no-cache`, `TZ=UTC`; snapshot ids are checked (hex) before
  they reach its argv.

## Restore flows

**One app** (`restore-<app>[@t]`, `melissa-server backup restore-app <app> [t]`): pick the files
snapshot (that run, or the latest) and the dump of the same run; the app must be deployed (if it was
uninstalled: deploy it again from the spec in `app.json`, then restore). restic restores into
`staging/restore-<app>`; the app is scaled to 0 and waited for; its Secret values are applied
(server-side apply, field manager `melissa-backup`); each backed-up volume is swapped into the
volume's current path by rename (the replaced data stays as `<path>.pre-restore` until the next
restore); volumes left out (dump excludes) stay as they are; the app is scaled back; then, for a dump,
when the hook's container is ready, `restic dump` is piped into `kubectl exec -i ... restore.command`.
Every step lands in the report (`last_restore` in the status). Tested end to end against real restic
with a fake cluster (`crates/backup/tests/restic.rs`).

**Whole device** (library functions, tested; the first-run UI comes later):
1. `Device::adopt`: point the config at the drive; the marker says whether the recovery key is needed;
   restic must open it with the key and report the marker's repository id.
2. `Device::restore_state`: swap the state directories in (the server stopped), keeping this device's
   excluded entries (voice model, `server.toml`) and the replaced copies as `*.pre-restore`.
3. Apps: deploy each from its `app.json` spec, then restore it as above (not automated yet).
4. Optional, same k3s version only: `Device::restore_k3s` puts the raw datastore, token, TLS and
   secrets key back (k3s stopped). `k3s::place` refuses another version.

Default for identity (PLAN Q112): a restored device keeps its name and settings (`device.json`,
people, chats, providers) and gets a fresh cluster and Tailscale identity (node key, cluster tokens and
`cluster.toml` are never in the state backup; apps come back through their logical export).

## Formats

- `config.json`: `{"version":1,"target":"/run/melissa-backup/usb1","encrypted":true,"repo_id":"…",
  "schedule":{"every":"weekly","day":"sun","hour":3},"retention":{"daily":0,"weekly":4,"monthly":6}}`.
  `schedule` may be `{"every":"daily","hour":h}` or `{"every":"off"}`. Retention: each 0-400, not all 0.
- `status.json`: `version, target, encrypted, ready, repo_id, schedule, retention, next_due, running
  {action, started, step}, last_backup, last_ok, last_restore, recovery_key_pending, problem`; a report
  is `{trigger, started, finished, ok, error, items: [{item, ok, mode, snapshots, bytes_added, message}]}`.
- Schedule: the hourly timer runs the backup when no attempt was made since the latest slot, or the
  last attempt failed with nothing successful since the slot and 6 h have passed (a drive plugged in
  later).
- Retention: `forget --prune --host melissa --group-by host,tags --keep-daily/weekly/monthly`. restic
  also keeps the oldest snapshot while there are fewer periods than asked for.

## Risks and limits

- **Unencrypted backups** hold provider sign-ins, app Secret values, k3s's CA keys and the secrets-at-rest
  key in the clear on the drive. The UI must recommend encryption plainly.
- **Recovery key at rest**: the device copy (root 0600) and, until confirmed, the server's readable copy
  (0640 root:melissa). Anyone with root on the device can read the backups anyway.
- **Same disk**: nothing stops a target on the same disk as `/var` (useful for tests, useless against
  a disk failure). The drive helper should refuse or warn.
- **Restores need space**: staging plus `.pre-restore` copies can double an app's footprint (PLAN Q36).
- **Credentials inside dumps** (MariaDB/MySQL root password from env): a restore into a reinstalled
  app works only once the Secret values are back (they are applied before the app starts).
- **Live copies** (`live`, and files next to a dump) are crash-consistent at best.
- **restic upgrades**: the JSON output may grow; the parser ignores unknown fields and message types.
- **Not done**: the drive helper (mount, label, unplug, same-disk check), Settings UI, a periodic
  `restic check`, notifications on failure, Nix packaging (the root unit is container-only), offsite
  targets (M4: a VPS or rest-server), automatic redeploy of missing apps in a whole-device restore.
