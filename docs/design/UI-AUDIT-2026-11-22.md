# Melissa web UI: building-block audit and standardisation proposal

Research only, 2026-11-22. Nothing in the repo was changed. Sources: `crates/web/assets/melissa.css` (6222 lines),
`crates/web/assets/melissa.js` (2149 lines), `crates/web/src/components.rs` + `src/components/*.rs`, and the
modules that emit maud markup (`pages.rs`, `settings/*.rs`, `ui.rs`). Rules read first: AGENTS.md, the
`melissa-ui` skill, `docs/agent-skills/ui-craft.md`, DECISIONS.md (2026-11-18 component library, 2026-11-20
workspace, 2026-11-21 motion, 2026-11-22 no fades / looks from the server), PLAN.md open question 75.

Line numbers are `melissa.css:<line>` unless a Rust file is named. Metrics came from a small CSS parser run over
the file (953 rules, 2911 declarations outside `:root`), then spot-checked by hand.

**All of this is a proposal.** Per the `melissa-ui` skill (rule 1) and the owner's memory notes ("Web UI: ask
first", "design in Penpot first"), nothing below should be built before the owner has seen the Penpot library
and approved the values marked **owner decision**.

---

## 0. Summary

**What's already fine:** colour is almost fully tokenised. Outside `:root`, colour properties use `var(--…)`
526 times and a literal 4 times. The only raw colours left are `.banner-close:hover` `rgb(0 0 0 / 0.06)`
(:279), `.msg-user .file-chip` `color-mix(…)` (:2284) and the provider-logo `#000`/`#fff` (:5193, :5198,
:5205; on purpose, brand rule). Weights are already a 4-step scale (400/600/650/700).

**What isn't:** everything about **size** is hand-written per rule, and the CSS is organised **by page**
(Sidebar, Chat, Composer, Panels, Details…), not by component. Every page grew its own button, row and pill.

| Measure (outside `:root`) | Count |
|---|---|
| `var(--…)` uses | 597 (all colour, font family, `--radius`, plus local hex geometry) |
| px literals | 428 |
| rem literals | 716 |
| `border-radius` declarations | 99, **14 distinct values**, only 17 use `var(--radius)` |
| `font-size` declarations | 142, **22 distinct values**, 0 tokens |
| `padding` declarations | 164, **89 distinct values** |
| `gap` declarations | 145, 23 distinct values |
| `min-height` declarations | 80, 19 distinct values |
| Heights of clickable controls | **10 distinct**: 28, 32, 34, 36, 38, 40, 44, 48, 52, 56px |
| Button-like classes | ~40 (list in §1.1) |
| Focus ring | 3px in 8 rules, 2px in 7, one uses `--action` instead of `--focus` (:4036) |
| Selector defined twice at top level far apart | 16 (two of them conflict: `.pill`, `.panel-close`) |
| Distinct classes in the CSS | 437 |

**Top inconsistencies**

1. **Buttons:** one base rule (`button`, :187: 44px min, `0.5rem 1.1rem`, radius 10, 1rem) and ~40 classes that
   override it into 10 heights, 6 radii (999px, 50%, 12, 10, 8px) and 8 font sizes (0.78–1.1rem). "Thick" is
   the base: 1rem × 1.5 line height + 8px padding top and bottom + 1px border on each side = 42px, raised to 44px.
2. **`.pill` is defined twice with different values** (:1147 for the sidebar/chat-head status, :4444 for app
   health). The second one wins for both. The chat header's "Working" pill gets `--ground` background, 0.85rem
   type and `0.1rem` padding, not the 0.8rem pill the 2026-11-20 design asked for.
3. **Three tone vocabularies** for the same meanings: `Tone` → `.tone-ok/info/warn/error/muted`
   (components.rs:20), `Health` → `.h-ok/h-busy/h-problem/h-idle`, and ad hoc `.pill.attention/.working`,
   `.approval.destructive`, `.chip-warn`, `.menu-item.danger`, `.seg.danger`.
4. **Inputs come in 7 flavours:** `.field input` 44px/r10 on surface, `.search-box input` 44/r10, `.picker-search`
   40/r10 on ground, `.settings-search` 40/r10 on ground, `.side-search input` 44 with no border, `.select-wrap
   select` 40/**r12**, `.inline-form select/input` 40.
5. **Radius doesn't follow size:** a 44px `.icon-button` has radius 8 (:5046), the same-size `.panel-close` has
   10 (:3263), a 40px `.select-wrap select` has 12 (:4883, the card radius), `.attach`/`.voice` (40px) have 12.
6. **The 44px rule is already broken on desktop in 13+ places:** banner close, copy code, file-chip remove,
   composer status link, picker "more", permission Review (all 32px), hex "more" (28), segmented (34), favourite,
   model chip, service ⋯ (36), picker levels (38). So "thinner" isn't a new exception, it's tidying one up.
7. **Two "link styled as button" components:** `external_button` (components.rs:2540) and `link_button`
   (components/provider_add.rs:12), both `a.button-like`. Its CSS (:4078) repeats the button metrics by hand.
   So does `.confirm-inline > summary` (:4010).
8. **`button.ghost` is misnamed:** it is a full-width secondary with a top margin (:214), and the approval card
   re-styles it into a real ghost (:1861).
9. **Markup outside the component library** (rule 2 of `melissa-ui`): `settings/pages.rs` (forms, inputs,
   `button.secondary` at :1246–1250, `label.field` + `input` at :1336–1338, `section.setting-group` blocks),
   `settings/add_provider.rs` (`button.secondary` :609, `button.link` :669, headings), `pages.rs` (`p.empty`
   :1206/:1208, layout divs).
10. **Small text is 22 sizes:** 0.85rem ×41, 0.8 ×31, 0.9 ×20, then 0.875, 0.95, 1.1, 0.75, 0.72, 0.78, 0.82,
    0.925, 0.92, 1.02, 1.05… (ui-craft already flags this, PLAN Q75a).

### 1.2 Links styled as buttons

- `external_button` (components.rs:2540): `a.button-like.primary`, new tab.
- `link_button` (components/provider_add.rs:12): `a.button-like` + `primary`/`secondary`.
- `a.button-like` CSS (:4078/:4119) repeats the button metrics; secondary has a border, primary a matching
  border colour. Neither shares a rule with `button`.
- `a.suggestion` (onboarding.rs:99) is a pill link; `a.menu-item` (agent.rs:143) is a link styled as a menu row;
  `a.tab` (panel.rs:365) a link styled as an icon tab.

**Missing for theming:**

1. **No layers.** Each token is both a raw value and a role. A theme has to restate every hex code; a
   high-contrast or "warm" theme can't change one palette step and have every role follow.
2. **No explicit switch.** Only `prefers-color-scheme`. There's no `data-theme`, so the user can't pick light
   or dark per device, and a third theme has nowhere to go.
3. **No size tokens at all** except `--radius`: no spacing, type scale, control heights, radius scale,
   border widths, shadows, motion, z-index.
4. **Missing semantic roles:** success-soft and info-soft backgrounds (badges and notices can't be filled),
   warning separate from brand honey (`.tone-warn` reuses `--honey-text`), hover/pressed/disabled colours,
   selected bg, strong border, overlay surface (menus use `--surface`, overlays use `--ground`), text on honey.
5. **Component values baked into rules:** 44px heights, `1.1rem` padding, `10px` radius, `0 12px 32px`
   shadows, 38×22 switch, 34px segmented… a theme with "compact" density or a different corner style has to
   edit ~400 declarations.

### 3.3 Thinner buttons and the 44px rule: trade-off

The `melissa-ui` skill and ui-craft §1/§7 say every control is at least 44px. The owner wants thinner buttons.
These conflict on a mouse-driven desktop, so the rule has to change, and that's an owner decision. Options:

| Option | How | For | Against |
|---|---|---|---|
| **A. Coarse pointer gets 44 (recommended)** | Component tokens default to 32/28; `@media (pointer: coarse)` sets `--button-height-md: 44px`, `--button-height-sm: 36px` plus a hit-area pseudo-element to 44 | Phones and tablets keep today's targets; desktop gets the thin look; one token switch, no per-component media queries | Hybrid devices: a touchscreen laptop reports `pointer: fine` (the primary pointer) and gets 32px targets for touch. `any-pointer: coarse` fixes that but then thick buttons come back on every touch laptop even with a mouse. Pick one; I'd use `pointer: coarse` |
| B. Invisible hit area everywhere | `.btn { position: relative } .btn::after { content:""; position:absolute; inset: -6px 0 }` → 32 + 12 = 44 tall | Same look everywhere, touch-safe | Hit areas of stacked controls overlap unless spacing ≥ 12px (ui-craft: "hit areas never overlap"); `position: relative` on every button; doesn't work for `overflow: hidden` parents (menus, sheets) |
| C. Keep 44 and thin the look | 44px box, smaller font and lighter border/fill | Rule untouched | Doesn't look thinner; the owner's complaint is the box size |

Recommendation: **A, with B only for `sm` icon buttons inside dense rows on coarse pointers** (where a 44px box
won't fit), and rewrite the rule as "visible ≥ 28px on fine pointers; ≥ 44px target on coarse pointers; target
spacing ≥ 8px". That still clears WCAG 2.2 AA (2.5.8, 24×24 minimum) everywhere and AAA (2.5.5, 44×44) on touch.
It does lose AAA on desktop, where 13+ controls already miss it. Inputs follow the same tokens so a field and its
button line up in `one_field_form`. On coarse pointers inputs stay 44px with 16px text (no zoom on focus).

### 3.4 Token architecture

Three layers. CSS names are the Penpot token path with dots → hyphens, so a token called
`color.bg.surface` in Penpot is `--color-bg-surface` in CSS, and the mapping is mechanical (a test can check it,

**Switching.** Colours use `light-dark()` so each semantic colour is declared once and the scheme picks the
side. `data-theme` sets `color-scheme`; `prefers-color-scheme` is the default when nothing is set:

```css
:root                    { color-scheme: light dark; }      /* follow the system */
:root[data-theme="light"] { color-scheme: light; }
:root[data-theme="dark"]  { color-scheme: dark; }
:root { --color-bg-canvas: light-dark(var(--color-neutral-50), var(--color-neutral-950)); /* … */ }
/* further themes override only layer 2: */
:root[data-theme="contrast"] { --color-border-default: …; --color-text-muted: …; }
/* density follows the pointer, not the theme: */
@media (pointer: coarse) { :root { --button-height-md: 44px; --input-height-md: 44px; --row-height-default: 44px; } }
```

`light-dark()` is in all current engines (Chrome 123, Firefox 120, Safari 17.5). The fallback for older
browsers is the existing pattern: one `@media (prefers-color-scheme: dark) :root:not([data-theme="light"])`
block plus the same values under `:root[data-theme="dark"]`. That duplicates the dark values, which is why
`light-dark()` is the better choice.

The server writes `data-theme` on `<html>` from a cookie the same way `looks.rs` does for the sidebar and banner
(DECISIONS 2026-11-22 (4)), so nothing flashes on load and the CSP stays strict. Breakpoints can't be custom
properties inside `@media`; keep them as documented literals (1200, 760/761, 560, 520, 40rem).

**Penpot mapping.** Penpot's design tokens (DTCG-style JSON) group tokens into sets, and its themes switch which
sets are active. Suggested structure (check against the local Penpot version's token types):

- Sets: `primitives/color`, `primitives/size`, `semantic/light`, `semantic/dark`, `component/default`,
  `density/touch`.
- Themes: group `Mode` with `Light` (primitives + semantic/light + component) and `Dark`; group `Density` with
  `Pointer` and `Touch`.
- Token types: color, spacing, sizing, dimension, border-radius, border-width, font-size, font-weight,
  font-family, shadow, opacity.
- Library components named by the same paths, `Button / Primary / md`, `Input / Search / md`,
  `Badge / Attention` (or Penpot variants with the axes kind/size/state if the version has them), so a
  designer's component name, the maud function and the CSS class say the same thing.
